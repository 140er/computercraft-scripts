# Gemini fleet design review

What this change does: Gemini proposes shared voxel memory, movement reservations, cooperative mining, a warehouse, DirectGPU views and AR controls. This review checks the proposal against main `9120c8e`, the supplied six documents, the installed jars and CraftOS-PC 2.8.3. It implements no feature.

## 1. TL;DR — do not paste these files into production

1. **P0:** Doc2's movement lock fails open on timeout; detours and vertical moves bypass it. It cannot enforce collision safety.
2. **P0:** Doc2 creates shared anchor/order table references; saving raises `Cannot serialize table with repeated entries`. Its delete-then-move save can also lose the only database.
3. **P0:** Doc4/5 DirectGPU calls have wrong signatures and a nonexistent rectangle/size API. DirectGPU **is installed**, and `directgpu` **is correct**. Keep it as the primary rendering target.
4. **P0:** V2 workers do not understand V3 server directives. Missing RPC correlation, sender checks and authentication allow lost, stale or forged commands.
5. **P1:** The proposed navigation is greedy axis stepping, not pathfinding. Boot coordinates, interrupted turns/moves and restart resume are unsafe compared with existing miner code.
6. **P1:** Four-block strip spacing plus front/up/down inspection does not expose all blocks; the vein algorithm can miss lateral branches and repeatedly select its occupied target.
7. **P1:** Warehouse code walks to chest blocks, sucks arbitrary items, ignores partial drops and never completes server orders. Charging must support the actual turtlebattery/SBW arrangement.
8. **P1:** Doc6 targets absent AP AR methods. Reuse cc_ar `ar_controller`, `fleetview.lua` and existing hub/server ownership. Full doc6 Lua was not supplied, only a six-line summary.

## 4. Key design corrections and server budgets

Extend root `server.lua`, not replace it with `server/server.lua`. Preserve legacy minearmy/roomsorter protocols during migration. Server owns durable job/map revisions; turtles still need a small local movement journal and cached safe return path. SSOT cannot atomically move Minecraft blocks and commit a network transaction; pending moves require restart reconciliation. One movement owner handles queued UI/network commands so a manual step cannot interleave with a worker turn after a yielding turtle API call. ESTOP must cancel queued work as well as set state, and remain effective during return-to-hub.

Reservations must cover all six movements, renew safely and distinguish a granted-but-not-started move from a started-but-unconfirmed move. Do not simply expire offline occupied cells or clear them all on boot and assume they are empty. Validate actual GPS/heading and reconcile in-flight moves before reopening those cells. Retries need operation IDs and duplicate result caching; a second SUBMIT_ORDER must not place a second physical order.

Live settings supplied in `server-configs.txt`: computer disk **4,000,000**, floppy **125,000** bytes; one computer worker thread; main global budget 10 ms and per-computer main budget 5 ms. The 5 ms budget applies to main-thread computer tasks, not a blanket five-millisecond Lua instruction timeout. Long nonyielding Lua work can still hit the roughly seven-second watchdog; actual-mod timing is authoritative. A* expansions, flood fill, map scans and draw loops need bounded batches with timer yields, cancellation and measured worst-case elapsed time. `parallel` is cooperative, not extra CPU cores; repeated large serialization still stalls everyone. A single textutils.serialize call cannot be made incremental by placing sleep after it.

Measured 1,000 sparse AIR records: **152,789 bytes default**, **93,788 compact** in CraftOS. Thus about 26k/default or 42k/compact records would fill 4 MB **before scripts, orders, temporary files and backups**. A complete 16^3 chunk in that shape is roughly 626 KB default; roughly three such chunks plus a same-size recovery generation already consume most of disk. Actual metadata/coordinates change these estimates. Keep compact chunk-local indices, interned block names, sparse unknown, bounded resident chunks, dirty journals and map retention/export policy. Reserve staging/recovery space; 4 MB does not make whole-world tables viable. Lua table heap cost exceeds serialized bytes; no measured heap ceiling is asserted here. Explicitly measure Lua/Java memory and garbage collection under fleet load.

CC:T modem inspection (`ModemPeripheral.transmit`) shows channel validation then an in-server Packet, not JSON or textutils serialization and not an HTTP-sized network upload. **Do not invent a 64 KB/128 KB rednet message ceiling** or confuse it with HTTP/websocket limits. Bound application packets anyway (initial policy: <=8 KiB encoded pages and <=64 cells, configurable after measurement), rates and outstanding requests; benchmark serialization and table conversion. Recursive/functions/metatables are not valid wire schemas. textutils default serialization rejects repeated tables, cycles and functions; deep recursion/large string allocation can exhaust stack/time/memory even when the structure is legal. Existing `server.lua:42` copies repeated references into independent tree values; retain that discipline.

Modem channels are 0..65535 with **128 simultaneously open per modem**; rednet protocols do not require one channel per protocol. Native wireless has live **64** low-altitude / **384** high-altitude range; ender is unlimited and cross-dimension for loaded endpoints. An ender server alone does not turn an ordinary turtle modem into an ender upgrade. Classic Peripherals' actual ender upgrade/range fix must be included and checked both directions. GPS hosts and moving turtle chunks must tick; rednet does not load them. [CC modem reference](https://tweaked.cc/peripheral/modem.html).

Turtle inspect/detect sense adjacent blocks only; inspect does not inventory a chest, prove traversability against entities, or remotely discover a vein. Do not permanently turn no-fuel/entity/protection failures into bedrock. Validate map observations and distinguish temporary traffic, fluids and dig permissions. AP geo_scanner is an optional separate sensor: scan results are relative offsets which must be translated using scanner origin, not turtle-facing coordinates. It does not make front/up/down coverage claims true for turtles lacking that hardware.

### DirectGPU monitor/wall contract

`META-INF/neoforge.mods.toml` says modId directgpu, version 1.0.25-neoforge-1.21.1, NeoForge >=21.1.0, Minecraft [1.21.1,1.21.2), CC >=1.117.1, BOTH sides. GPU block registration/resources and turtle/pocket upgrade resources are present. Peripheral type constant is exactly directgpu. Monitor detection resolves named/nearby Minecraft monitor block geometry, with width/height/facing; it creates a **separate pixel display aligned with that monitor surface**, not a CC text terminal wrapper. Prefer an explicit advanced-monitor name/side over ambiguous nearest selection, and verify wired/named attachment on the real setup.

Monitor walls are detected as aggregate geometry and receive one sized display; base resolution is **164 pixels per block on each axis** at scale 1, configurable scale **0.1..4.0**. Thus a 3x2 wall is 492x328 at scale 1; these are calculated dimensions, not a captured runtime result. `getDisplayInfo` returns actual dimensions. Jar guards limit physical display width/height to 1..16 blocks, legacy integer multiplier to 1..4, and explicit pixel axes to 1..4096 (`MAX_SIZED_RESOLUTION=4096`). Do not hardcode 512x320 or infer monitor dimensions from text scale. Resizing/rebuilding a wall requires rediscovery and layout/input recalibration.

The 3D API delegates to `DirectGPU3DRenderer`: software rasterization occurs on the server side; calling the design hardware-accelerated is misleading. Main target: **textured/voxel DirectGPU view on ordinary advanced monitors and multiblock advanced walls**. Implement real scene camera, cube/model geometry, texture loading and bounded visible chunk sets. Doc4's 2D side/top textured tiles remain useful alternate projections; text fallback is separate.

The jar also ships `data/directgpu/computercraft/lua/rom/apis/directgpu_term.lua` and the matching `rom/modules/main/directgpu_term.lua`: its Lua helper reads getDisplayInfo pixel dimensions and expands palette colors into separate RGB channels. Reuse/probe that provided terminal adapter for terminal content where useful; it does not implement the requested voxel scene. termRedirect/termRender are exported too.

Live `frameCache3D=true`, `occlusionCulling3D=true`, `clearDisplaysOnDetach=true`; maxUpdatesPerSecond=0 and maxKBpsPerDisplay=0 mean **unlimited**, not safe automatic throttling. Config descriptions say excess updates merge, and excess bandwidth collapses commands to a compressed frame. Static frame cache benefits unchanged scenes/camera/lights/textures; clearing/rebuilding or orbiting every telemetry tick defeats reuse. Dirty-frame rendering, small visible sets, delta mode where tested, explicit redraw limits and a load benchmark are required. Detach/shutdown clears displays; recreate after reconnect. getDisplayFrameJpeg is useful server-buffer diagnostic evidence but **not** proof of a client rendering a physical monitor wall.
